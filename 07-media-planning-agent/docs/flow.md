# メディア選定エージェント v30 — 処理フロー解説

> このツールが「要望」を受けてから「提案レポート」を出すまで、内部で何をどの順にやっているか。
> ソース：`ptc_media_agent_v30.py`

---

## 入力 → 出力

- **入力**：要望＋条件（例：「製造業向けの記事タイアップを7件」＋ `filters` / `weights`）
- **出力**：提案レポート（7媒体の価格・メニュー・選定理由をまとめたHTML＋要約テキスト）

**ひとことで言うと：** 「メディア一覧のExcel」から要望に合う媒体を**点数付けで選び**、各媒体の**資料PDFをAIに読ませて**価格や広告メニューを書き起こし、**提案レポートにまとめる**自動化ツール。営業は `main("要望", params)` を1回呼ぶだけ。

---

## 処理の流れ（上から順に実行）

```
main(要望, params)
  │
  ├─ 0. 準備        main()                元データ(Excel)を取ってくる            ✅ 正常
  │
  ├─ 1. スコアリング score_media()         選ぶ（filters＋weightsで点数化）        ⚠️ 一部穴あり(#4・#5)
  │
  ├─ 2. PDF取得     step2_get_pdfs()       集める（OneDriveからDL・並列）          ✅ 概ね正常
  │
  ├─ 3. 提案生成    _gen_single_proposal() 読む・書く（PDF→AIで抽出）             🔴 故障(★1)
  │
  ├─ 4. 予算チェック step4_budget_check()   調整する（予算超過を外す）             ✅ 正常
  │
  └─ 5. 出力        build_html_report()    まとめる（HTML＋stdout印字）           ⚠️ 並び・リンク乱れ(#5)
```

### 各ステップの中身

| STEP | 役割 | 関数 | やっていること | 例 |
|---|---|---|---|---|
| 0 | 元データ取得 | `main()` | OneDriveの「/メディア」からマスタExcelをDL | メディア選定システム_50col.xlsx |
| 1 | **選ぶ** | `score_media()` | filtersで絞り、weightsで加点、合計点で上位7件を確定 | 業種_製造 × 5 で加点 |
| 2 | **集める** | `step2_get_pdfs()` | 各媒体の資料PDFをDL（名前照合）。DL完了順に次を先行開始 | MONOistの媒体資料PDF |
| 3 | **読む・書く** | `_gen_single_proposal()` | PDFを画像でAIに渡し価格・メニュー・理由・比率%を抽出。失敗時は5回リトライ→空dict | 「¥130万〜／2,000PV保証／…」 |
| 4 | **調整する** | `step4_budget_check()` | 予算指定時に超過媒体を外し不足を補充。未指定ならスキップ | 予算500万円で絞り込み |
| 5 | **まとめる** | `build_html_report()` | 純PythonでHTML生成＋詳細をstdout印字 | 7媒体の比較表＋予算シミュレーター |

---

## 別ルート：深掘り（2回目以降）

```
handle_turn2()   「この媒体を詳しく」の追加要望で呼ばれる、STEP1〜5とは別の入口
   前回の選定結果(ptc_state)を参照して続きを処理する「はず」だが…
   → 呼ばれるたびにスクリプトが丸ごと再実行され、状態が毎回リセット
   → ptc_state が常に空       🔴 故障(★2)：ERROR: ptc_stateが空です
```

---

## どのステップに、どの不具合があるか

| ステップ | 不具合 |
|---|---|
| STEP1 選ぶ | #4 規模データ欠損でゼロ点／#5 重み無指定で `score 0.0`（無選別） |
| STEP2 集める | DL完了順で先行処理するため、出力がスコア順にならない（#5） |
| STEP3 読む・書く | ★1 大判PDFを画像で読めず **要問合せ・空欄**。失敗理由は表に出ず、下流AIが暴走→誤情報（#3） |
| 出力 | 並び順・PDFリンクの乱れ（#5） |
| 深掘り | ★2 **ERROR: ptc_stateが空です** — 状態リセットで常時失敗 |
| 全体を覆う | #7 診断ログが重く処理が最大215秒。ログ形式が#3の暴走も悪化させる |

---

## まとめ

「選ぶ（STEP1）」と「集める（STEP2）」はほぼ正常で、壊れているのは **「読む・書く（STEP3）」と「深掘り（handle_turn2）」**。だから直すべき本命はこの2箇所、という結論につながる。
