# 人物辞書（人 DB）自動構築 — 設計書（実装済み・最終版）

> 2026-07-14 実装完了。検索時の人物名寄せ（表記ゆれ解決）と会社→担当者の逆引きのため、
> 4媒体（Gmail/Zoom/Slack/Drive）の保存処理が登場人物を「人」DB に自動登録する。
> 検索OS（notion_集約 v3 予定）の resolve_person がこのDBを読む。

- 人物辞書DB「人」: `<PEOPLE_DB_ID>`（meta > 人）
- 実装済み: Gmail v2 3本・Zoom latest 2本（`PEOPLE_DB_ID` 定数で接続）
- slack_recorder_v5 / drive_recorder_v4 用: `人物辞書_移植パッチ_slack_drive.md` を貼り付け

---

## 1. DB スキーマ（4列・スモールスタート）

| 列名 | 型 | 中身 | 更新ルール |
|---|---|---|---|
| name | タイトル | 代表表示名（例: 担当A） | **初回観測時に設定、以後変更しない**（表示の安定。名前が取れなければメール） |
| email | テキスト | 小文字正規化したメールアドレス | **主キー（upsert の match）**。不変 |
| aliases | テキスト | 観測した全表記を改行区切りで蓄積 | 新表記を set マージで追記（増えるだけ・消さない＝**冪等**）。複合表示名「担当A / Tomomi Mashiko」は `/`・`｜` で分割した各部分も蓄積（短い単位の方が contains 検索でヒットしやすい）。Slack はプロフィールから display_name / real_name / ハンドルを一括登録（移植パッチ参照。初回シードスニペット付き） |
| company | テキスト | **メールの@より後ろの文字列そのまま**（判断なしの事実） | email から機械導出。会社名・PJへの意味づけは**手動のドメイン情報DB**が担い、読む時にドメイン文字列で結合する |

- 検索OSの `resolve_person` は「name / aliases / email を contains 検索」する実装のため
  この列構成で無改修接続できる（active 列は無し→全員有効扱い。必要になったら手動列として追加可）
- role 等の手動列は後から自由に追加してよい（スクリプトは定義済み列しか触らない）

## 2. 誰を登録するか（媒体別）

| 媒体 | 登録する人 | 材料 |
|---|---|---|
| Gmail（3本・実装済み） | From と To の全員 | `_extract_name_email_pairs`（名前⇄メールの対応を保って抽出。**この対応情報は保存の瞬間にしか存在しない**——保存後は name 列と sender/to 列に分かれて失われるため、ここで確保するのが本設計の核心） |
| Zoom（2本・実装済み） | メールが取れた参加者＋ホスト | participants の name+email |
| Slack（パッチ） | 投稿者 | user_map の表示名⇄メール |
| Drive（パッチ） | 最終更新者 | lastModifyingUser |

**登録しないもの:** CC/BCC（名前が取れずノイズが多い。初版対象外）/ メールが取れない人
（email が主キーのため）/ 機械アドレス（noreply 等の部分一致ブロックリスト `_PEOPLE_EMAIL_BLOCKLIST`）

## 3. 更新ロジック（共通ヘルパー `_upsert_people`）

```
_upsert_people(persons)   persons = [{name, email}]
  ├ email で集約（同一実行内の重複をまとめ、書き込みを人数分に抑える）
  ├ 人物ごとに:
  │   1. 人DB を「email equals」で1クエリ検索
  │   2a. 行なし → create（name=観測名 / aliases=観測名 / company=ドメイン）
  │   2b. 行あり → aliases を set マージ、name は既存維持
  │   3. upsert（match: email equals）
  └ 失敗は WARN のみで続行（★本体の保存を絶対に巻き込まない）
      PEOPLE_DB_ID が空なら全体をスキップ（安全に無効化できる）
```

コスト: 1人あたり Notion 2呼び出し（読み1＋upsert1）、**LLM ゼロ**。

## 4. 呼び出しタイミング

- **トリガー系**（受信時・送信時・録画時）: 本体の保存成功の直後に都度実行
- **バッチ系**（Gmail過去情報・Zoom過去情報）: 保存中はメモリの `_people_buffer` に
  収集し、**run() の最後に人物ごとに直列で書き込み**
  （16並列の保存中に都度書くと同一人物のマージが競合するため。
   まとめ書きなら競合ゼロ＋書き込みが「件数」でなく「人数」で済む）
- トリガー同士の稀な競合でマージが負けても、次の登場で再マージされる（**自己修復**）

## 4.5 呼び名（会話内のニックネーム）の扱い

「ましこさん」のような会話内の呼び名は**保存時に抽出しない**（本文からの人物紐付けは
LLM の推測になり、間違いが辞書に権威として残るため。辞書は観測された識別子のみ）。
代わりに検索側（v3 の resolve_person）が**クエリの表記変換**（ましこ→担当A/Mashiko/mashiko）
を生成して aliases に照合する。Slack ハンドル名（ローマ字）がひらがな⇄ローマ字の橋渡しになる。
定着した呼び名は aliases 列への**手動追記でOK**（set マージ実装のためスクリプトに消されない）。

なお Slack はシード＋プロフィール一括登録で初回にほぼ完成するため、以後の投稿ごとの
更新は「新入メンバー・プロフィール変更の追従」という保険の役割（投稿1件+2クエリの低コスト）。

## 4.6 逆引き（Zoom）の照合仕様と既知の限界

- 2段階照合: ①敬称（さん/様等）・括弧内所属・「 - 会社名」サフィックスを除去して contains
  → ②0件ならトークン分割（空白/camelCase境界・1文字トークン除外）の AND 照合
  （「Ayano Ito さん」「Ito Ayano」「AyanoIto」「田中太郎(営業部)」等に対応。実測検証済み）
- どの段階も**一意ヒット時のみ採用**。既知の限界（許容する制約）:
  - 同姓同名が辞書に複数いる場合は常に見送り（誤結合よりマシ）
  - 1〜2文字の短い名前は複数ヒットで見送りになりやすい
  - 転職・改姓（メール変更）は別人物行になる（辞書は事実のみ。必要なら手動で aliases を相互に足す）
- aliases の2000字切り詰めは撤廃済み（_rt のチャンク分割で全量保存）

## 5. ネガティブ影響と対策（検討済み）

- 同名別人の混在 → 行は email 別に分かれる。読む側（v3 resolve_person）で
  「複数人ヒット時は混ぜず候補提示」にする（v3 実装時の宿題）
- 個人データの集約 → 人DB の閲覧権限は raw DB と同等以上に絞る（Notion 側の運用）
- 錆び（退職者・ゴミ行） → 自動では消えない。気づいた人が行を消す運用
  （aliases は冪等なので、間違って消しても実在の人なら次の登場で復活する）

## 6. 将来の保険: 全再構築

raw DB＋Gmail/Zoom API には全ての登場記録が残っているため、人DB は常に再導出可能。
増分更新がズレた・壊れた・スキーマを変えたくなった場合は、過去情報バッチの再実行
（人物収集が同梱されている）や専用の再構築スクリプトでいつでも作り直せる。

## 7. 検討して不採用にした代替案（経緯の記録）

| 案 | 不採用の理由 |
|---|---|
| projects/回数/last_seen 等も持つ8〜9列版 | 回数はバッチ再実行で二重カウント・媒体間で単位不揃い。「登場PJ」はクエリ時に raw から引ける（sender contains 等）ため辞書に持つ必然性が無い。**クエリで代替できない「名寄せ（aliases）」だけに絞った** |
| people＋登場記録の2DB正規化 | 「1行=1人で完結する台帳」でなくなる |
| people DB を作らずクエリ時2ホップ解決のみ | 名前⇄メールのペア情報が raw の列分離で失われており、確定的な解決には保存時の記録が必須と検証で判明 |
| 会社マスターDB / ドメイン情報DBへの列追加（承認キュー含む） | プロジェクト⇄ドメインの意味づけは**手動管理**とする方針（2026-07-14 ユーザー決定）。company 列のドメイン文字列と読む時に結合すれば足りる |
