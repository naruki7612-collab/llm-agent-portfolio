# 01 — 知識集約・横断検索基盤

Slack / Gmail / Google Drive / Zoom に散らばった社内のやりとりを1つのDBに集め、
自然言語の質問に出典付きで答えさせる仕組みです。個人で設計から運用まで担当しました。

## 構成

```
書く側（recorders/）                     読む側
─────────────────────          ──────────────
slack_recorder.py    ─┐
gdrive_recorder.py    │
gmail_inbound.py      ├─→  統合DB（raw）  ─→  search_os_v4.py
gmail_outbound.py     │     ＋ 人物辞書          ＋ 人物名寄せ
gmail_backfill.py     │     ＋ ドメイン対応表    ＋ スレッド復元
zoom_on_recording.py  │                          ＋ 深読み
zoom_backfill.py     ─┘                          ＋ 出典必須の合成
```

| ファイル | 役割 |
|---|---|
| [`search_os_v4.py`](search_os_v4.py) | 検索OS本体。プランナー→取得→再計画→深読み→出典付き回答 |
| [`search_os_v3_notion.py`](search_os_v3_notion.py) | 同じ仕様の旧バックエンド版。制約の違いが差分に出ている |
| [`recorders/`](recorders/) | 各ソースから統合DBへ書き込む収集スクリプト |
| [`docs/`](docs/) | 設計ドキュメントとシステムプロンプト |

## 設計で効いた判断

**DBを1つにした。** 当初はソースごとにDBを分ける案でしたが、
「誰が・いつ・何を言ったか」を横断で引くたびに結合が必要になるため、
11プロパティの単一テーブルに統合し、ソース別の突合キーだけ分けています。

**バックエンドの制約は仕様ではなく実装に閉じ込めた。**
`search_os_v4.py` の移植先は部分一致検索と `$or` を持ちません。
検索の仕様（キーワード横断、人物名寄せ、スレッド復元）は変えず、
完全一致で絞ってから Python 側で照合する二段構えに移しています
（`_keyword_match` / `_person_match`）。
その結果、取得モードが2つに分かれます
— キーワード無しは降順ソートで1発、キーワード有りはページングで全走査してローカル照合。

**人物の名寄せを3層にした。** メールアドレスを主キーにしつつ、
表示名の揺れとドメインからの所属推定を別テーブルに持たせています。
`noreply@` のような機械アドレスはブロックリストで人物として登録しないようにしています。

## 引っかかった点

- タイムスタンプに `+00:00` と `+09:00` が混在していました。突き合わせは必ずUTCに正規化してから行います
- メール取得APIの受信トレイ指定フィルタが、**成功ステータスを返したまま0件を返す**という壊れ方をしていました。検索クエリ側で絞る形に変更しています
- 返信メールは前文を全部引用するので本文が肥大します。ただし `> ` で始まる行を落とす素朴な実装は本文まで消すため、区切り文字の一覧で切っています
