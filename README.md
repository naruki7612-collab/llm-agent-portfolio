# LLM エージェント実装ポートフォリオ

業務で設計・実装した LLM エージェントと、それを支える周辺スクリプトを集めたものです。
すべて社内のエージェント実行基盤（Python サンドボックス + ツール注入）の上で動かすことを
前提に書いています。

- Python **52ファイル / 36,408行** ＋ 設計ドキュメント14本
- 領域: 文書分類、帳票の読み取りと転記、請求書突合、横断検索、外部SaaS連携
- 共通の作り: 構造化出力（JSON Schema）での LLM 呼び出し、段階分割したパイプライン、
  実データでの精度計測、再実行可能なキャッシュ

> **匿名化について** — 業務案件の成果物のため、社名・人名・メールアドレス・データベースIDは
> すべて架空の値に置換しています。何をどう置き換えたかは [SANITIZATION.md](SANITIZATION.md) に
> 全ルールを載せました。処理ロジックには手を入れていません。

## 設計上、意識していること

### 段階を分けて、途中結果を残す

02 の仕訳パイプラインは `s10_ingest` → `s20_extract` → `s30_vouchers` → `s32_group_llm`
→ `s35_split` → `s40_classify` → `s50_export` → `s60_feedback` の8段です。
各段が中間成果物を書き出すので、分類だけやり直す・特定の伝票だけ再実行する、が効きます。
LLM の呼び出しは高価で不安定なので、**1本の長いプロンプトにまとめない**ことを優先しました。

### 精度は実データで測る

02 には `eval/eval_by_line.py`（行単位）と `eval/eval_by_voucher.py`（伝票単位）を同梱しています。
粒度を変えると数字が変わるため、両方を出して報告しています。

評価で踏んだ失敗を1つ。**正解の手がかりをプロンプトに書かない**。
LLM 呼び出しのたびに渡されるので下駄になり、行単位で 18pt の差が出ました。
実例を載せたいときは、評価期間ではなく学習期間から採って、規則の形に書き換えています。

### 確信度は品質保証にならない

02 の仕訳分類で、「モデルの確信度が高いものは自動確定してよい」という前提を検証したところ、
自動確定に回した分の **15% が誤り**でした。確信度と実際の正誤が対応していないので、
この設計は成立しません。

そのため 03 の債務者区分判定では確信度による足切りを採らず、
**判定根拠をセルに出力させる**方式にしています
（`credit_rating_agent.py` の `OUTPUT_CELLS['判定根拠']`）。
自動で確定させるのではなく、人が根拠を見て確認できる形に倒した、という判断です。

### 原本を壊さない

05 では openpyxl で既存ブックを開いて保存し直すと、印刷設定やシェイプが失われることが分かりました
（実測で印刷設定27個と図形が消失）。既存ブックの一部セルだけを更新する箇所は、
xlsx の ZIP を直接編集する方式に切り替えています。

### 落ちるときは黙って落ちない

外部APIには「成功を返しながら空を返す」ものがあります
（例: メール取得APIのフォルダ指定フィルタが機能せず、成功ステータスのまま0件を返す）。
件数が0のときに正常終了しないよう、取得系には件数チェックを入れています。

## `agent_sdk` について

スクリプトは社内基盤が実行時に注入する SDK を前提にしています。基盤自体は社内資産なので、
このリポジトリには**シグネチャとドキュメントだけを持つ空実装**を置いています
（[agent_sdk/__init__.py](agent_sdk/__init__.py)）。

提供される主な機能:

| 関数 | 用途 |
|---|---|
| `llm_call(prompt, model=, schema=, files=)` | LLM 呼び出し。`schema` で構造化出力、`files` でPDF等を添付 |
| `rag_download(files=[{index_name, file_name}])` | 登録済みファイルをサンドボックスに取り寄せる |
| `tavily_search` / `tavily_extract` | Web検索と本文抽出 |
| `tool_bridge(tool_slug, params)` | Gmail / Drive / Zoom / Notion 等への汎用ブリッジ |
| `db.table(name).find(filter)` | DataTable への問い合わせ |

そのままでは動きません。動かすには実基盤か、同等のアダプタ
（任意の LLM SDK + ベクタ検索 + KVS）を差し込む必要があります。

### 基盤の制約と、それに対する設計

実行環境には次の制約があり、スクリプトの構造はこれに強く影響を受けています。

- **1回の実行に時間上限がある**（呼び出し方により約300秒〜15分）。セッションが変わると一時ファイルが消える
  → 長い処理は状態を外部DBに逃がして再開可能にする（01 のバックフィル、09 のSlackエクスポート）
- **並列実行の上限が16**
  → `asyncio.gather` + `Semaphore(16)` で頭打ちに合わせる
- **DataTable に部分一致検索と `$or` が無い**
  → 完全一致で絞ってから Python 側で照合する二段構え（01 の `search_os_v4.py`）
- **添付は約64MB、pptx は非対応**
  → 大きなPDFはページ分割してから渡す
