# 09 — 汎用ツール

特定の案件に紐づかない、手元で使っているツール類です。

## [`slack-export/`](slack-export/) — Slackチャンネルのエクスポート

チャンネルの履歴とスレッド返信を取得し、Markdownに整形して書き出します。

| ファイル | 役割 |
|---|---|
| `slack_lib.py` | API呼び出しの共通処理 |
| `slack_export_resumable.py` | 再開可能なフルエクスポート |
| `slack_incremental.py` | 差分取得 |
| `render_to_project.py` | 取得結果をMarkdownに整形 |

**再開可能にしているのは、遅くて落ちるからです。**
1リクエストあたり15件の上限に加えてレート制限が頻発し、
実測で115メッセージ＋返信682件の取得に36分掛かりました。
途中で切れても続きから再開できるよう、取得済みのカーソルを状態ファイルに書いています。

ページングは**同一ページの検知が必須**です。カーソルが進まないまま同じページを
返してくる場合があり、終了条件を件数だけに頼ると無限ループになります。

## [`outlook-triage/`](outlook-triage/) — メールの仕分けと下書き

3段構成です。

```
step1_categorize_mail.py    受信メールを分類
step2_extract_attachments.py  添付を取り出す
step3_create_draft.py        返信の下書きを作る
```

段を分けているのは、分類だけ回したい／添付だけ取り出したい、が実務で頻繁にあるためです。

## [`gmail-label/gmail_label_agent.py`](gmail-label/gmail_label_agent.py)

受信メールを分類して Gmail のラベルを付けます。ラベルは2階層です。

```
要対応  ─ 要対応/<組織名>      自分が動かないと止まるもの
予定                            日時が決まる・決まっているもの
取引    ─ 取引/<組織名>        お金が動くもの
配信                            読み物。読まなくても困らない
通知                            機械が出した記録
その他
```

**親を6つに固定しています。** カテゴリを増やすと、どれに入れるべきか曖昧な
メールが増えて分類が揺れます。分類器の精度以前に、定義が重なった時点で破綻します。

**子ラベルは一部の親にだけ切ります**（`ORG_SUBLABEL_PARENTS`）。
あとで組織単位で掘り返したくなるのは「要対応」と「取引」で、
配信や通知まで組織で割るとラベルが増えすぎて、探すコストがかえって上がります。

**子ラベルは事前に用意しません。** 分類のたびにラベル一覧のキャッシュを引き、
無ければネスト名のまま作ります。組織は増え続けるので、
人が先にラベルを掘る運用にすると必ず追いつきません。

判定の作りとしては、複数該当したときに上位を優先し、必ず1つ選ばせています
（該当なしを許さない）。未分類が溜まると結局人が全部見ることになるためです。
取りこぼすより、多めに拾って人が下げるほうが安い、という前提を
プロンプトにも明記しています。

システムラベル（`INBOX` / `STARRED` / `IMPORTANT` 等）は付与対象から除外しています。
既読状態や受信トレイ在席を書き換えると元に戻せません。

## [`calendar-agent/`](calendar-agent/)

自然文から予定を作成・参照します。
スクリプト本体はRAGから取り寄せる方式で、毎回コードを生成し直しません。

## [`product-search/product_search.py`](product-search/product_search.py)

商材マスタを5列に絞ってルーティングに特化させた検索ライブラリです。
価格列を持たせる案は却下しました。更新頻度が違うものを同じテーブルに入れると、
マスタ全体が古くなるためです。

## [`agent_system_prompt_template.md`](agent_system_prompt_template.md)

エージェントのシステムプロンプトの雛形。案件ごとに書き起こすのをやめて、
共通の骨格（役割 / 入力 / 手順 / 出力形式 / 禁止事項 / 失敗時の振る舞い）を固定しています。
